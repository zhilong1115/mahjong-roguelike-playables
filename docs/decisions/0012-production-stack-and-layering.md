# 0012 — 正式代码的技术栈与分层

状态：`Accepted`（技术选择，可随时按「回退条件」推翻）

日期：2026-07-26

实现：`src/`

## 背景

原型阶段已经回答了「玩什么」：14 张结构牌、六开运位、三签选一、五系构筑（`0009`–`0011`）。
现在要回答「用什么写」，并把 `prototype/v3-arcade-demo/` 里被验证过的东西搬进 `src/`，
之后所有玩法改动只在 `src/` 发生，原型只作历史对照。

## 决定一：原生 ES Module + JSDoc，不引入 TypeScript 与打包器

目前仓库零依赖：没有 `package.json`，测试直接用 `node --test`，试玩只要一个静态服务器。
这条链路的价值在这个阶段大于类型系统：

- 改一行就能刷新，不用等构建；试玩和自动化测试跑的是同一份文件。
- YouTube Playables 要求自包含离线包，越少构建魔法越容易保证产物可控。
- 内容表都是纯数据对象，JSDoc + 编辑器推断已经能挡住大部分手滑。

代价是没有编译期类型检查。缓解方式：

- 所有模块写 JSDoc typedef，导出全部具名，禁止默认导出。
- 规则、内容、结算、存档一律有自动测试兜底。
- 目录和文件按「一个职责一个文件」切分，迁移到 TS 时是逐文件加类型，不需要重构。

**回退条件**：当内容条目超过约 80 件，或出现第二个人长期并行开发时，
引入 TypeScript + esbuild，先把 `src/core` 和 `src/content` 转过去。

## 决定二：保留像素 Canvas 牌面渲染器

`04-technical-architecture.md` 里悬而未决的「是否保留当前像素 Canvas 牌面渲染器」——保留。
它满足零外部请求，34 个牌种全部运行时自绘并缓存，缩放到任何整数倍都锐利。
DOM 负责布局与交互，Canvas 只负责牌面与像素字。

## 决定三：目录分层

```text
src/
├── core/        规则内核：tiles / patterns / shanten / deal / effects / scoring / run
├── content/     五系内容表与关卡表，纯数据 + 少量抽签函数
├── state/       存档序列化与版本迁移
├── render/      像素绘制
├── ui/          界面、动画、音效
├── platforms/   平台适配层接口与 web 实现
├── main.mjs     启动组装
└── index.html
```

强制方向：`ui → core → content`，`core` 不引用 `ui/render/platforms`，
`render` 不认识玩法概念（只吃 tile 和字符）。这样核心规则可以在 Node 里直接跑测试，不需要 DOM。

## 决定四：结算流水线输出「有序步骤」，动画只是它的播放器

`core/scoring.mjs` 按 `0011` 的八步顺序算分，并产出 `steps[]`，每一步带：
来源（base / group / slots / bone / seal / pattern / codex / charm / general / total）、
本步的牌值 / 番势 / 金币、累计后的牌值与番势、以及一个动画锚点。

这条决定同时解决三件事：

1. 结算过程可解释——界面直接照着 steps 逐条播，玩家看到的顺序就是规则顺序。
2. 结算过程可测试——测试断言 steps 的顺序与累加自洽，不需要跑动画。
3. 动画不参与算分——快进、`prefers-reduced-motion`、后台标签页都不会改变结果。

## 决定五：存档存「完整手内状态」，不靠 seed 重放

`state/save.mjs` 把手牌、牌墙、已亮组、灵签、五系构筑整份写进存档，带 `schemaVersion` 和逐版本迁移函数。
不采用「只存 seed + 操作序列」的重放式存档：规则一改，旧档就会静默算出不同结果。
解析不了的档一律返回 `null`，由上层决定是否开新局，绝不静默覆盖。

## 与原型的关系

`prototype/` 下三个 Demo 全部冻结为历史对照，不再跟进玩法改动。
`src/` 的规则内核以 V3 为基线，但做了这些收敛：胡牌分解与番种识别拆成 `patterns.mjs`，
距离计算拆成 `shanten.mjs`，五系效果统一由 `effects.mjs` 解释，结算改为步骤化。
